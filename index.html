Skill voor Claude Code

Grote features bouwen in stappen die je kunt controleren

buildflow laat Claude Code een grote feature opknippen in kleine checkpoints. Elke checkpoint moet langs vaste gates: de tests en een review door een agent die ervan uitgaat dat de code fout is. Verandert er iets op het scherm of in de docs, dan komen daar een UI-check tegen het prototype en een controle van de documentatie bij. Bij drie of vier stops beslis jij mee, afhankelijk van of er iets zichtbaars verandert; met --brief of --auto zijn het er minder. Daartussen werkt Claude door.

Zo begin je

Pak de zip uit in je skills-map en start in Claude Code:

/buildflow <wat je wilt bouwen>

Doe dat in de map van je project, met een schone git-tree. buildflow maakt zelf een branch buildflow/<slug> aan, met een korte naam voor de feature als slug.

Waarom

Wat je eraan hebt

Voor een bugfix of een kleine aanpassing heb je dit niet nodig. Het gaat lonen bij features waar je normaal een middag of langer mee bezig bent, en waar je halverwege niet meer precies weet wat er allemaal is aangepast.

3–4stops waar Claude op jou wacht, met --brief of --auto minder
4gates per checkpoint, twee alleen als ze nodig zijn
4–12checkpoints, meestal
0pip-pakketten nodig

Eerst afspreken wat je bouwt

Voordat er iets ontworpen of gepland wordt, praat Claude met je over het probleem, de gebruikers, wanneer het geslaagd is en wat er buiten de scope valt. Je krijgt twee of drie aanpakken met een advies. Vragen die de code kan beantwoorden, stelt hij niet. Het resultaat is brief.md, en elke agent leest die daarna als het contract.

Een checkpoint is pas klaar met bewijs

Tests worden eerst geschreven en moeten eerst falen, om de goede reden. Pas dan komt de code. Een gate gaat alleen op groen met testaantallen, screenshots of het oordeel van een reviewer erbij, en het script dat de run bijhoudt weigert stappen die niet mogen, zoals checkpoint 3 starten voordat 2 klaar is.

Niemand keurt zijn eigen werk goed

De code-review doet een agent die aanneemt dat de code fout is. Na elke fix kijkt een nieuwe reviewer, met de vorige bevindingen erbij. De UI-reviewers zien alleen het goedgekeurde prototype en de draaiende app, niet de instructies van het project. Ze beoordelen wat er op het scherm staat.

De hoofdsessie schrijft zelf geen code

Eén orchestrator houdt de regie en geeft elke klus aan een subagent met een schone context. Zo blijft elke agent bij zijn taak, ook als de feature uren duurt, en loopt de context van de hoofdsessie niet vol met code die hij niet hoeft te zien.

Je ziet wat het kostte en waar de tijd zat

Na elke checkpoint krijg je een rapport: per gate het resultaat, het aantal pogingen, de bevindingen, de duur en de kosten, uitgesplitst per rol, per checkpoint en per model. Het bedrag is een API-equivalent en niet je rekening. Hoe dat zit, staat bij wat een run kost.

Alles in één bestand dat je kunt doorsturen

De viewer is één HTML-bestand met het plan, de voortgang per gate, de kosten en de learnings. Hij werkt op je telefoon, je kunt hem printen naar PDF en je stuurt hem door zonder dat er iets ontbreekt.

Hoe het werkt

Fases, stops en gates

Tussen de stops werkt Claude door zonder op je te wachten. Bij de gele stops ligt de beslissing bij jou. De designstop komt er alleen bij als de feature iets zichtbaars verandert.

  1. Contextprojectprofiel en wat de feature raakt
  2. Briefbrainstorm, dan brief.md stop
  3. Designdesign.md en prototype, alleen bij UI stop
  4. Plancheckpoints en testplan stop
  5. Bouwenelke checkpoint door de gates, daarna de docs
  6. Reviewjij probeert de feature stop

De vier gates per checkpoint

1

Gedrag

De geplande tests worden eerst geschreven en moeten dan falen, omdat het gedrag nog ontbreekt en niet door een typfout of een kapotte import. Daarna schrijft een agent code tot ze slagen, zonder de tests aan te passen. De tests van eerdere checkpoints moeten groen blijven.

2

UI alleen als het zichtbaar is

Twee reviewers vergelijken de draaiende app met het goedgekeurde prototype, de een op uiterlijk en de ander op gedrag. Elk verschil krijgt een ernst en een plek op het scherm. Kwam de stand van het scherm niet overeen met de referentie, dan telt de vergelijking niet en doen ze hem opnieuw. Zolang er een blocker of high openstaat, gaat de gate niet door.

3

Review

Een adversary neemt de diff door en probeert te bewijzen dat hij fout is. Een fixer lost de bevindingen op, of laat met bewijs zien waarom een bevinding niet klopt. Dan draaien de tests opnieuw en kijkt een nieuwe reviewer. Is er na vier rondes nog geen akkoord, dan pauzeert de run en krijg jij de vraag.

4

Docs alleen als er docs veranderen

Een agent werkt de bestaande documentatie bij, op de plek en in de vorm die je project al gebruikt. Een tweede agent controleert elke gewijzigde bewering tegen de code. Na de laatste checkpoint volgt nog één docs-gate over de feature als geheel.

Waarom het zich aan de regels houdt

Afspraken in een prompt zijn geen garantie, dus buildflow dwingt ze op twee manieren af. Het script bf.py houdt de stand van de run bij en weigert stappen die niet mogen: bouwen zonder goedgekeurd plan, een gate passeren terwijl een eerdere nog openstaat, gedrag goedkeuren met falende tests. En een Stop-hook laat Claude zijn beurt niet afsluiten zolang er in de bouwfase gates openstaan.

Die hook is niet blind. Wachten op subagents die op de achtergrond lopen mag gewoon, en als hij een paar keer achter elkaar blokkeert zonder dat er iets verandert, geeft hij het op in plaats van Claude eindeloos rond te laten draaien.

Het idee komt van Shopify, dat de methode beschrijft in Helix, en van de uitwerking van AI Labs op YouTube. buildflow is een eigen uitwerking van dat idee, zonder code van Shopify. De brief, de designfase, de rapportage van kosten en tijd en het projectprofiel dat features delen, zitten in geen van beide. De UI-review doen hier twee Claude-subagents, waar Helix Gemini gebruikt.

Handleiding

Stap voor stap

Per fase wat je krijgt en wat er van jou verwacht wordt. Bij een gele stop wacht Claude tot jij iets zegt.

0

Context

Claude leest je project voordat hij iets vraagt

Wat je krijgt

  • .buildflow/context.md, een profiel van je project: stack, conventies, tests, hoe je de app draait en het bestaande design. Volgende features gebruiken het opnieuw.
  • .buildflow/<slug>/context-feature.md, wat deze feature in de code raakt en welke bestaande features je kunt navolgen.
  • Een nulmeting op de achtergrond: installeren, bouwen, tests draaien, dev-server starten.

Wat je doet

Open Claude Code in de map van je project en typ /buildflow met een zin of een alinea over wat je wilt bouwen. Zorg dat je git-tree schoon is, anders vraagt buildflow eerst wat je ermee wilt.

Verder niets. Tests die nu al falen, lost Claude niet stilletjes op. Die komen als randvoorwaarde in de brief.

1

Brief

Samen het probleem en de aanpak scherp krijgen
stop

Wat je krijgt

  • Vragen in korte rondes, steeds met een aanbevolen antwoord erbij.
  • brief.md met het probleem, de gebruikers, wanneer het geslaagd is, wat er wel en niet in zit, de gekozen aanpak en de risico's.
  • De viewer met de brief, en een samenvatting van vijf regels in de chat.

Wat je doet

Beantwoord de vragen. Meestal zijn het twee of drie rondes. Lees daarna de brief in de viewer en kijk of het probleem, de scope en de aanpak kloppen. Wat anders moet, zeg je in de chat of typ je in het feedbackvak van de viewer. Is het goed, zeg dan "akkoord".

Heb je al een uitgewerkte spec, start dan met --brief spec.md. Claude checkt hem op gaten en slaat het gesprek over.

Design

Alleen als de feature iets verandert wat gebruikers zien

Wat je krijgt

  • design.md in de docs van je project, aangevuld waar hij al bestaat.
  • Prototypepagina's met alle states uit de brief, gebouwd met je eigen front-end: Storybook als je dat hebt, anders statische pagina's met de echte CSS van je app.

Wat je doet

Klik door het prototype en zijn states, en kijk of het eruitziet en werkt zoals je wilt. Geef wijzigingen door of zeg "akkoord". Het design wordt daarna met de feature gecommit, en de UI-gate vergelijkt later alles hiermee.

Bij backend-werk, of als er al een goedgekeurd ontwerp is, slaat buildflow deze stap over en zegt waarom.

Plan

De feature opgeknipt in kleine checkpoints
stop

Wat je krijgt

  • Een plan van meestal 4 tot 12 checkpoints, van simpel naar complex, elk met wat "klaar" betekent.
  • Per checkpoint de tests die dat bepalen.
  • In de chat de checkpoints op een regel elk, welke een UI-gate krijgen, en de open vragen en aannames.

Wat je doet

Loop de checkpoints na. Je kunt per checkpoint een opmerking typen in de viewer en alles in één keer kopiëren met "Kopieer feedback voor Claude", of gewoon in de chat antwoorden. De planner past het plan aan en je ziet het opnieuw.

Pas na jouw akkoord wordt er iets gebouwd.

4

Bouwen

Checkpoint voor checkpoint door de gates

Wat je krijgt

  • Een commit per checkpoint.
  • Na elke checkpoint een rapport in de chat en als bestand in .buildflow/<slug>/reports/: per gate het resultaat, de pogingen, tests, bevindingen, duur en kosten.
  • Een viewer die steeds de laatste stand laat zien.
  • Na de laatste checkpoint een docs-gate over de hele feature, zodat design.md en het prototype kloppen met wat er echt gebouwd is.

Wat je doet

In principe niets. Na elk rapport gaat Claude meteen door met de volgende checkpoint. Wil je live meekijken, vraag dan om bf.py serve --open. Dat geeft een viewer die zichzelf elke paar seconden ververst.

Loopt een gate vier keer vast, dan pauzeert de run en krijg je één concrete vraag met een advies.

Stopt Claude door een rate limit terwijl de sessie nog openstaat, dan is "ga verder" genoeg. Na een crash, een dichtgeklapte laptop of in een nieuwe sessie typ je altijd opnieuw /buildflow. Die ziet dat er een run loopt en vraagt of je hem wilt hervatten, en zet meteen de hooks en rechten van de skill weer aan. Wil je het oude gesprek terug, open het dan met claude --continue of claude --resume, maar typ daarna nog steeds /buildflow. In alle gevallen kijkt Claude eerst wat de stand is en doet hij een onderbroken stap opnieuw, in plaats van een resultaat aan te nemen dat niemand heeft gezien.

Review

Jij test de feature en accepteert of geeft feedback
stop

Wat je krijgt

  • Het eindrapport, final.html, met de hele feature bij elkaar.
  • In de chat precies hoe je de feature probeert: het commando, de URL, een testaccount en waar je op klikt.

Wat je doet

Probeer de feature zelf. Wat je anders wilt, wordt een paar nieuwe kleine checkpoints die door dezelfde gates gaan, plus een regel in learnings.md die elke agent voortaan als eerste leest. Verandert je feedback het probleem zelf, dan past Claude eerst de brief aan.

Ben je tevreden, zeg dan dat je het accepteert. Claude sluit de run af en biedt aan een PR te openen en het eindrapport als private Artifact te publiceren.

Installeren

Klaarzetten in vier stappen

Zo staat buildflow klaar voor al je projecten. Wil je hem in één project, bijvoorbeeld om met je team te delen, kijk dan onder de stappen.

  1. Download de zip

    Met de knop bij Download, of in je terminal:

    curl -L -o buildflow.zip https://github.com/joepvanabeelen/buildflow-website/releases/latest/download/buildflow.zip

  2. Pak hem uit in je skills-map

    mkdir -p ~/.claude/skills
unzip -o buildflow.zip -d ~/.claude/skills

    De zip bevat één map, buildflow, met daarin de skill en de LICENSE. Na het uitpakken staat alles dus in ~/.claude/skills/buildflow. Laat de mappen scripts en references naast SKILL.md staan. De Stop-hook zoekt scripts/gate_hook.py precies op deze plek. Staat het ergens anders, dan doet de hook stilletjes niets en kan Claude tijdens het bouwen stoppen terwijl er nog gates openstaan.

  3. Kijk of het script draait

    python3 ~/.claude/skills/buildflow/scripts/bf.py doctor

    Het script print de map van de skill, de projectmap, je Python-versie en de modellen waarvoor een prijs in pricing.json staat. Zolang er geen run is, eindigt het met "no active run". Meer controleert het niet.

  4. Start je eerste run

    Open Claude Code in je project en typ:

    /buildflow <wat je wilt bouwen>

    Zie je /buildflow niet, start dan een nieuwe sessie. Met --brief spec.md geef je een spec mee die je al had, --lang nl of --lang en kiest de taal van alles wat jij te lezen krijgt (zonder --lang neemt hij de taal waarin je schrijft), en --auto slaat de goedkeuringen over.

Wat je nodig hebt

  • Claude Code
  • Python 3.9 of nieuwer, alleen de standaardbibliotheek. Je hoeft niets met pip te installeren.
  • git
  • Voor de UI-gate een browsertool in Claude Code: Playwright MCP of Claude in Chrome.
In één project installeren, bijvoorbeeld voor je team

Download de zip in de map van je project, net als bij stap 1, en pak hem uit in .claude/skills. Commit die map mee, dan werkt iedereen in het team met dezelfde versie. De zip zelf kun je daarna weggooien.

cd pad/naar/je-project
curl -L -o buildflow.zip https://github.com/joepvanabeelen/buildflow-website/releases/latest/download/buildflow.zip
mkdir -p .claude/skills
unzip -o buildflow.zip -d .claude/skills
rm buildflow.zip
python3 .claude/skills/buildflow/scripts/bf.py doctor

De Stop-hook kijkt eerst in ~/.claude/skills/buildflow en daarna in .claude/skills/buildflow van het project. Staat buildflow op allebei, dan draait de hook dus het script uit je homemap.

Vragen

Beperkingen en vragen

Eerst wat buildflow niet kan, daarna de rest.

Werkt het ook buiten Claude Code?

Nee. buildflow leunt op dingen die Claude Code heeft: een skill met hooks, subagents met een eigen context en de transcripts waaruit kosten en tijd worden berekend. In andere tools of chatomgevingen doet het niets.

Wat moet er op mijn machine staan?

Python 3.9 of nieuwer en git. Het script gebruikt alleen de standaardbibliotheek, dus er valt niets te installeren met pip. Voor de UI-gate heeft Claude Code een browsertool nodig, Playwright MCP of Claude in Chrome.

Wat kost een run?

Dat hangt vooral af van de grootte van de feature. Elke gate draait met eigen subagents en een review kan een paar rondes duren, dus reken op een flink aantal tokens. Het rapport laat per checkpoint, rol en model zien waar ze heen gingen.

Het bedrag in de rapporten is wat het via de API tegen lijstprijs gekost zou hebben. Met een Claude-abonnement betaal je niet per token, dus het is niet je rekening. Het is wel een eerlijke maat om runs met elkaar te vergelijken.

Kan ik tussendoor iets anders vragen in dezelfde sessie?

Het kan, maar alles in een sessie die aan de run gekoppeld is, telt mee in het rapport, van de start tot je accepteert. Stel losse vragen dus liever in een andere sessie.

Moet ik bij elke stop zelf goedkeuren?

Nee, start dan met --auto. Alleen de eindreview blijft bij jou. Meer daarover staat onder de handleiding.

Wat gebeurt er bij een rate limit of een crash?

Bij een rate limit of een API-fout legt een hook de onderbreking vast en markeert hij de gate die op dat moment liep als onderbroken. Een crash laat geen spoor na, dus daar kijkt Claude zelf naar als je terugkomt. Hoe je verdergaat, staat bij de fase Bouwen. Een stilte van meer dan tien minuten telt in het rapport niet als bouwtijd.

Mijn feature heeft geen scherm. Heb ik hier dan iets aan?

Ja. Dan slaat buildflow de designstap over en draait de UI-gate niet. De gates voor gedrag, review en docs blijven gewoon staan.

Kan ik een plan of rapport met iemand delen?

Stuur viewer.html of final.html door. Beide bevatten alle data zelf, er hoeft niets bij. Je kunt Claude na afloop ook vragen het eindrapport als private Artifact te publiceren, dan heb je een link die je deelt wanneer je wilt.

Run-data staat standaard buiten git, via .buildflow/.gitignore. Wil je de rapporten committen, haal dat bestand dan weg.

Hoe werk ik bij naar een nieuwe versie?

Haal de oude map weg en pak de nieuwe zip uit met hetzelfde commando als bij de installatie:

rm -rf ~/.claude/skills/buildflow
unzip -o buildflow.zip -d ~/.claude/skills

Je runs staan in .buildflow/ in je project, niet in de skill, dus die blijven staan.
